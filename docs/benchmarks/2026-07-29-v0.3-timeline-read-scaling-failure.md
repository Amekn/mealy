# v0.3 timeline-read scaling failure

Date: 2026-07-29 (Pacific/Auckland)

This is negative pre-release evidence, not a durability result. The attempted v0.3.0 24-hour soak
did not produce a promotable `mealy.soak-report.v2` report. None of its elapsed time or completed
turns is carried into the replacement release gate.

The exact clean subject was commit `76aee260` and external `mealyd` SHA-256
`67b926f8c1a63daef7e472e0a10627e8f540c16caff3014d0c54fc83ae8e9d8a`. The systemd-supervised
run lasted 58,292 seconds (16 hours 11 minutes), reached timeline cursor 391,885, and then failed
when an authenticated timeline request exceeded the harness's ten-second client deadline. The
daemon had not restarted unexpectedly. Peak resident-plus-swap pressure was material: systemd
recorded about 1.3 GiB peak memory and 270.5 MiB peak swap.

The retained database is 1.18 GiB. A stopped full `PRAGMA integrity_check` returned `ok`; the
failure was a read-scaling defect, not database corruption. The original retained home remains
unchanged. Diagnostic work used reflinked copies.

## Diagnosis

Both timeline pagination and its preliminary high-watermark lookup built complete historical
session-membership sets across tasks, run lineage, attempts, tools, effects, approvals, validation,
delegation, claims, compaction, memory, artifacts, and messages. SQLite's plan materialized those
sets, fetched the complete session history, joined the global presentation stream, and created a
temporary ordering tree even when the caller requested only events after cursor 391,869.

The exact failed binary served an isolated near-current request in about 0.34 seconds after warmup,
but 16 concurrent requests saturated CPU, took roughly 7–14.5 seconds, and repeatedly crossed the
ten-second deadline. Resident memory grew from about 70 MiB to 388 MiB and remained allocated after
the burst. This reproduced the soak failure without provider, network, or write-path activity.

## Correction and focused validation

Timeline reads now deliberately scan the cursor-ordered presentation table first. Each candidate
event is resolved by primary key and checked through correlated, indexed lineage predicates. The
high-watermark lookup performs the same operation in descending order and stops at the first
session-owned event. A deliberate `CROSS JOIN` is the SQLite planner fence that preserves this
bounded access order.

Response-parity checks against every retained soak session matched the failed binary byte-for-byte
for stable pages at cursors 0 and 390,000. On the exact previously failing page, dirty-tree
diagnostic binary SHA-256
`0a9c3f7b12c05673cef534ac14dac49ec1656fb51dafa4fdf365dc3150142958` completed 256 requests at
16-way concurrency with 34 ms median, 42 ms p95, and 50 ms maximum latency. All 256 returned HTTP
200. Resident memory grew by about 2.5 MiB during the burst instead of about 318 MiB.

A deterministic regression inserts 50,000 same-session historical events, uses SQLite's virtual
machine progress callback to bound executed work, and verifies both the latest-cursor lookup and a
near-current timeline page. This is insensitive to host speed and fails if the implementation
returns to complete-history materialization.

The diagnostic is focused evidence only. The corrected clean commit must pass protected CI,
produce rebuilt packages, and start a fresh exact-binary 86,400-second soak from zero before v0.3.0
can be promoted.
