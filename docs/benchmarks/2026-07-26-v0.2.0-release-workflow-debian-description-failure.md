# v0.2.0 release-workflow Debian-description failure

Status: rejected release attempt; retained negative evidence

The annotated `v0.2.0` tag points to protected-main commit
`92801dcc0f43dfe88ceb6da5bcd7a1b15fa3ba5d`. Its
[release workflow](https://github.com/Amekn/mealy/actions/runs/30188985959) ran from
2026-07-26T05:11:43Z through 2026-07-26T05:32:41Z and failed before
publication. GitHub has no `v0.2.0` release. Repository signing, GitHub
release creation, asset attestation, Pages deployment, and public package or
repository acceptance did not run.

## Failure

Both `linux-x86_64-gnu` and `linux-aarch64-gnu` jobs stopped in
`Build reproducible release archive` only when the release-specific Lintian
gate inspected the completed Debian package:

```text
W: mealy: extended-description-line-too-long line 3
Process completed with exit code 2.
```

The third extended-description line in `DEBIAN/control` was 87 columns:

```text
 The companion client provides onboarding, setup, chat, operations, and administration.
```

The package lifecycle immediately preceding Lintian completed successfully on
both architectures. This was a Debian metadata conformance defect, not a
runtime, state, sandbox, architecture, or installation failure.

## Root cause and remediation

The production tag workflow installed Lintian and treated every warning as a
failure. Protected CI built the same deterministic Debian fixture, but its
fixture test neither installed nor invoked Lintian and did not independently
bound extended-description line length. That left a release-only validation
gap.

The corrected builder wraps the sentence at 71 and 16 columns and rejects any
absent or over-79-column extended description before constructing a package.
The Debian fixture independently checks the extracted control file and invokes
`lintian --fail-on error,warning`. Protected strict CI and every Debian-family
distribution container now install Lintian before running that fixture.

The pushed `v0.2.0` tag is historical public state and must not be moved,
deleted, or reused. The correction advances the application to `v0.2.1`.
Because that semantic-version change alters both release binaries' exact
identity, the corrected candidate must repeat exact-binary qualification and
the complete tag workflow; the successful `v0.2.0` runtime soak is retained as
evidence but is not relabeled.
